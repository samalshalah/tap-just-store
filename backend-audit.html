What the back end does, and what it can't do yet

A full read of the admin, the API routes, the data layer and the order path — with the work ranked in the order it has to happen.

17 stands live · 16 active, 1 draft · audit run 21 Aug 2026 against main @ 9c04a57

The store cannot take an order today

Not "checkout is rough" — there is no path from a product page to a paid order at all. Browsing runs on the new stands model; buying runs on the old dispensary products model; the two were never connected. The Continue button on every stand page is hard-disabled, and the only code that could ever put something in the cart belongs to orphaned components no route imports any more.

Even if something reached the cart, there is no payment provider anywhere in the codebase, no shipping address field, and the checkout asks for a pickup window. That is the centre of gravity for everything below.

Two unauthenticated holes turned up during the audit. I closed both before writing this — they were live on production and I wasn't willing to leave them open for the length of a report.

What genuinely works

More than you'd expect. This is a real storefront with a real admin — the gap is concentrated in one place.

  • The catalogue model. Stands, types, business uses and variants are properly normalised. A stand is tagged into categories, never duplicated. Draft stands cannot leak into the shop.
  • The storefront. Home, shop with search/size/finish/sort, 15 indexable landing pages, product pages, cart maths with volume tiers, legal pages, sitemap, FAQ structured data.
  • Money is in integer cents end to end in the new code, with one formatter. The old sale-price overcharge bug is fixed.
  • The stands admin — create, edit, delete, price, tag, upload three images, publish. Plus a shop-categories screen for the landing photos.
  • Theme, settings and branding are database-driven and applied server-side with no flash of unstyled content.
  • Order confirmation email is the best-written file in the repo: correct money formatting, HTML escaping, per-recipient error handling.
  • Deploy pipeline. Push to main → Cloudflare build → live. Schema drift now fails loudly via npm run check:schema.
  • Nothing can be added to the cart. StandBuyBox's CTA is disabled; the two components that call addItem are imported by no route.
  • No payments, no shipping address, no tax. Zero integrations — grep for stripe, paypal, square returns nothing.

The plan

Five phases. The order is not preference — each one is blocked by the one before it. Sizing assumes we keep working the way we have been.

01

Harden what's already live

Half a day · nothing depends on it, so it can go first

  1. Rate-limit the login and stop logging customer PII from the contact form.
  2. Give the session its own secret and a per-session nonce, so a stolen cookie can't be used to crack the admin password. Store the password hashed.
  3. Cap upload size, allow only real image types, and set the stored content type from the file rather than the browser's claim.
  4. Move the foreign keys, unique constraints and indexes into the Drizzle schema so db:push stops threatening to drop them. Index order_items.order_id and orders.created_at first.
02

The setup flow

The biggest single build · everything downstream waits on it

  1. Standard: paste your link → confirm → cart.
  2. Branded + QR: paste your link → upload logo → business name → we generate a real scannable QR → you approve a proof rendered on the front template → cart.
  3. Re-key the cart from productId to standVariantId and carry the setup data — link, logo, business name, approved proof — on the line item.
  4. Enable the Continue button. This is the moment the shop becomes a shop.
Gate: logo and business name are collected before the cart, never "we'll email you later". Proofs use a real generated QR, never a placeholder.
03

Take money

Blocked by 02 · the phase that makes the business real

  1. Repoint order_items at stand_variants, keeping the name and price snapshot so history survives a catalogue edit.
  2. Server-side pricing through pricing.ts — volume tiers recomputed on the server, never trusted from the client.
  3. Shipping address, shipping rate, sales tax. Retire the pickup-window field and the store-hours screen behind it.
  4. Payment provider. Fix the 100× cents-as-dollars displays, persist or remove the tip, and put a unique index and an idempotency key on order creation so a double-click can't double-charge.
  5. Move the stock read inside the transaction with a row lock and a non-negative constraint.
Gate: the legal pages already promise tracking numbers and a 30-day return window. Confirm the terms in src/lib/legal.ts before the first real order.
04

Run the business

Blocked by 03 · this is where you'll live day to day

  1. Order lifecycle beyond four free-text states: paid, in production, proof approved, shipped, delivered, refunded — with a state machine, not any-to-any.
  2. Tracking number field, a shipped email, and a customer-facing status page keyed on the confirmation code.
  3. Search, filter and pagination on orders. Cancelling restocks; cancelled orders leave the revenue figure alone.
  4. A production queue: which proofs are approved and waiting to print, exportable for your printer.
  5. Inventory for stands — stand_variants has no stock column at all today.
05

Clear the decks, then grow

Safe to start the deletions any time; the rest follows 04

  1. Delete the orphaned components and cannabis libraries. Retire /admin/products, categories, brands and the importer once nothing references the products table.
  2. Strip the dead settings screens, or wire them up — analytics is worth wiring, taxes belong in phase 03, the age gate and Weedmaps fields should go.
  3. Point the SEO checklist and the regenerate button at stands. Delete the DC neighbourhood pages.
  4. Either build /blog or remove the admin screen. Right now it publishes into a void.
  5. Hosted multi-link: the landing page builder, subscription billing, and the lapse behaviour your terms already describe.

What I need from you

Four calls I shouldn't make alone.

Payment provider

Stripe is the default answer for a US store selling physical goods with a subscription alongside — one integration covers both the one-off stand and the $9.99/month. Say the word and I'll build against it.

Who prints and ships

This decides the whole of phase 04. A print-on-demand partner with an API means we push approved proofs automatically. Printing in-house means we build a queue and you export files. Very different builds.

Terms in src/lib/legal.ts

Governing law is set to the District of Columbia; dispatch windows, the 30-day return window and the 12-month warranty are my defaults. They're published on your live site. Confirm or change them.

Delete the legacy catalogue?

It cannot go until the stands checkout replaces it — the order API still reads the products table. But I'd like your agreement now that it goes, so I build phase 03 for stands only instead of trying to support both.
